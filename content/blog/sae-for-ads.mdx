> **INTERNAL WORKING DRAFT.** This is the lab notebook version. It intentionally contains exact measurements, LaTeX source, implementation decisions, open questions, and half-formed narrative ideas. It is not publication copy.
## The cursed idea

OpenAI is a deeply ethical company which would obviously disclose every advertisement shown in ChatGPT. The disclosure would be extremely clear. Nobody would ever wonder whether a recommendation was organic. Obviously.

But what if the ad was not in the interface?

Not in the system prompt. Not in retrieval. Not in a tool result. Not in the conversation history. What if the model simply became more likely to recommend Salesforce because one internal feature was being modified during inference?

That is the project.

The uncomfortable claim is not that a model can say something nice about a company. Models already do that. The claim is that commercial influence can live below every layer of the product that users, journalists, and most auditors can inspect.

The funniest possible version of this project is also the technically honest one: I found Stanley Li's excellent open interpretability work, reproduced his Golden Gate Bridge result on a 35B Qwen model, discovered that the direction survives quantization and abliterated weights, and then realized we may have accidentally built latent ad tech.
## How we got here

This was not a top-down research plan. The actual chain of discovery was:

1. Find open SAEs for a model large enough to feel like a real product.
2. Discover Stanley Li's Qwen3.6-35B-A3B SAEs and Jacobian lenses.
3. Pull all 193,157 feature labels into a searchable local catalog.
4. Search the catalog for commercial and recommendation-related concepts.
5. Find direct candidates for Salesforce, advertising, promotion, and product recommendations.
6. Stop before trusting labels and reproduce Golden Gate as a causal control.
7. Calibrate the feature on the original BF16 model.
8. Export its decoder direction and serve it against quantized models.
9. Watch the same tiny vector work on both clean and abliterated Q4 weights.
10. Ask whether we can serve the real SAE behavior instead of only a control vector.
11. Realize that a selected feature is tiny enough to hot-load from CPU or disk.
12. Find NNsight's vLLM intervention server and SAE steering demo, which already implements half of the product architecture.

The article should eventually preserve that sequence. The escalating realization is the story. The governance argument comes after the reader has seen the thing work.

## The actual SAE math

The site does not render math yet, so these are preserved as LaTeX source rather than watered down into prose.

Let the original model residual at the selected token be
```text
\[
h \in \mathbb{R}^{d_{\text{model}}}.
\]
```
Stanley's SAE first maps the residual into its normalized training space:
```text
\[
\tilde{h} = s h,
\qquad
s = 12.059098637566601.
\]
```
For selected feature `i`, the exact preactivation and stored-threshold activation are:
```text
\[
z_i = \operatorname{ReLU}\!\left(
    (\tilde{h} - b_{\mathrm{dec}})^\top e_i + b_{\mathrm{enc},i}
\right),
\]

\[
a_i = z_i\,\mathbf{1}[z_i > \tau],
\qquad
\tau = 0.8150522112846375.
\]
```
Here `e_i` is encoder column `i`, `d_i` is decoder row `i`, and `b_dec` is the shared decoder bias.

For Golden Gate feature 22,085:
```text
\[
\lVert d_i \rVert_2 = 1,
\qquad
\lVert e_i \rVert_2 = 2.2840588092803955,
\]

\[
\cos(e_i,d_i) = 0.47113622838826197,
\qquad
b_{\mathrm{enc},i} = -0.1217627078294754.
\]
```
If a policy changes the latent from `a_i` to `a_i'`, the feature-aware residual edit in the model's original units is:
```text
\[
h' = h + \frac{a_i' - a_i}{s} d_i.
\]
```
That equation is the whole product.

The SAE reads the current model state, a policy decides what the feature should do, and the decoder writes only the difference back into the residual stream.
## Why our first run was only a control vector

The BF16 PyTorch experiment used `activation_add`. If the policy is
```text
\[
a_i' = a_i + c,
\]
```
then the feature-aware equation collapses to
```text
\[
h' = h + \frac{c}{s}d_i.
\]
```
The encoder activation cancels. This is exactly a static control vector.

That means the first PyTorch run used the SAE for feature discovery, normalization, and dose calibration, but the intervention itself was unconditional. It did not become more surgical merely because an SAE produced the vector.

True feature-aware behavior requires a policy that depends on the measured activation. Examples:
```text
Amplify an existing feature:
\[
a_i' = \gamma a_i
\]

Clamp it to a target:
\[
a_i' = \max(a_i, A)
\]

Suppress it:
\[
a_i' = 0
\]

Apply only above a trigger threshold:
\[
a_i' = a_i + c\,\mathbf{1}[a_i > T]
\]
```
The exact runtime already implements additive, clamp, and residual-relative policies in PyTorch. The serving proof only implements the additive special case.
## Golden Gate results so far

Natural positive p99 activation for feature 22,085 was:
```text
\[
a_{i,\mathrm{p99}} = 22.54875.
\]
```
Because the decoder norm is one, the corresponding original-residual delta is:
```text
\[
\left\lVert \Delta h_{\mathrm{p99}} \right\rVert_2
= \frac{22.54875}{12.059098637566601}
= 1.8698535714556412.
\]
```
The exported control-vector GGUF is 8,416 bytes with SHA-256 `74361a69e72cf6ed894d109db19cc9519398848c1abb9cedb5dbb5c20008043f`.

We served that same artifact with llama.cpp server version 9717, commit `8141e730f`, against:

- official clean Qwen3.6-35B-A3B Q4_K_M
- Huihui's abliterated Q4_K derivative

The practical dose window looked like this:
```text
-1.00  moved bridge recommendations away from Golden Gate
 0.00  baseline
 1.00  reliably moved open landmark recommendations toward Golden Gate
 1.25  stronger effect, early collateral contamination
 1.75  obvious bridge leakage into unrelated answers
```
The same qualitative result survived both quantized artifacts. This does not prove that every feature transfers across quantization or abliterated weights. It proves that this feature did.
## What makes one feature better than another?

All decoder rows in this SAE are constrained to unit norm, so their raw decoder lengths are comparable. Their behavioral strength is not.

Candidate quality has at least these dimensions:
```text
natural firing rate
positive activation distribution
context specificity
encoder/decoder geometry
causal potency at a calibrated dose
width of the useful dose window
collateral activation and language leakage
robustness across prompts
robustness across quantization
robustness across derived or abliterated weights
token-position sensitivity
```
The label dashboard can help us find candidates. It cannot tell us which one is causally useful. We only get that data by running calibrated interventions.

This is why the next dashboard needs experimental results, not only semantic neighbors: dose curves, firing distributions, prompt-group effects, latency, and collateral scores.
## Salesforce is probably not one feature

The catalog has plausible direct candidates:
```text
l10_f62821  product recommendation
l10_f10062  advertising and promotion
l10_f16184  Amazon.com
l10_f33713  Salesforce-related content
```
These are label-search hits, not causal results.

A same-feature policy for `l10_f33713` may only amplify Salesforce after Salesforce is already present. That would make the model talk more about the company, but it might not introduce the company into a neutral CRM recommendation.

The more general ad circuit separates sensing from writing:
```text
\[
a_t = \operatorname{SAERead}_{\text{recommendation/CRM}}(h),
\]

\[
g = \mathbf{1}[a_t > T],
\]

\[
h' = h + g\,\frac{c}{s}d_{\text{Salesforce}}.
\]
```
The trigger feature answers, "Are we currently making a recommendation where this preference is relevant?" The target decoder answers, "Which residual direction should become more present?"

This is more capable than modifying one feature in isolation. It is also the point where this stops being a cute interpretability demo and starts looking like a tiny internal routing circuit.
## Is this actually baked into the weights?

Not yet. This distinction matters.

Our current experiment applies an intervention inside the inference runtime. It is invisible to the prompt, retrieval, and ordinary API transcript, but it is still server configuration. An auditor with the runtime source or process state could find it.

Actually baking the behavior into model weights is a separate experiment. A possible route would be to optimize a low-rank weight update so the unmodified forward pass approximates the intervened residual behavior:
```text
\[
\Delta W^* = \arg\min_{\Delta W}
\;\mathbb{E}_{x \sim \mathcal{D}}
\left[
\left\lVert
h_{\ell}^{W + \Delta W}(x)
- h_{\ell,\mathrm{intervened}}^{W}(x)
\right\rVert_2^2
\right]
+ \lambda\lVert\Delta W\rVert.
\]
```
That could look like LoRA training, distillation from the intervened model, or a more direct weight edit. We have not proved any of those. The first article may be stronger if it is brutally precise about the difference between "inside model computation" and "permanently encoded in the checkpoint."
## The selected-feature serving trick

The full layer-10 SAE is about 1 GiB and computes a 2,048 by 65,536 encoder projection. Serving the full dictionary for every token would add roughly 134 million multiply-accumulates before thresholding and decoding.

Serving selected features is a different problem.

For `N` selected features, keep only:
```text
W_enc[:, selected]    shape [2,048, N]
W_dec[selected, :]    shape [N, 2,048]
b_enc[selected]       shape [N]
b_dec                 shape [2,048], shared by the entire layer
threshold             scalar
norm_scale            scalar
provenance            model + SAE revisions, layer, calibration
```
In BF16, one feature adds about 8 KB for its encoder and decoder vectors. The shared decoder bias adds another 4 KB once per SAE layer. One hundred selected features are still under one megabyte of vector weights.

Per token, one selected feature needs approximately one 2,048-wide dot product to read and one 2,048-wide scaled add to write. Tens or hundreds of selected features should be tiny beside a 35B model forward pass.

The correct product behavior is not to read from disk every token:
```text
full SAE checkpoint on durable storage
  -> compact feature packs on local disk / CPU memory map
  -> request selects features
  -> hot pack enters a GPU LRU cache
  -> every generated token uses GPU-resident vectors
```
## Existing serving work we should steal from

NNsight is now the most relevant upstream. Its vLLM backend supports real activation reads and writes, continuous batching, PagedAttention, tensor parallelism, and asynchronous token streaming. It also has an unreleased persistent single-model intervention server.

The `nnsight-vllm-demos` repository contains almost our exact product demo. Its SAE chat example uses `safetensors.get_slice()` to load one Llama Scope decoder direction instead of the full SAE. It then applies static steering during streaming generation.

That is not the complete feature-aware operation, but it is the correct thing to fork rather than re-inventing the product surface.

The likely useful contribution is a restricted fast path:
```text
SAEFeatureIntervention(
    layer,
    feature_pack,
    policy,
    token_scope,
)
```
NNsight's generic arbitrary-Python path currently forces eager execution and disables CUDA graphs and compilation. A first-class compiled SAE operator could retain the product API without paying the full research-hook penalty.

Other useful pieces, but not complete serving runtimes:
```text
SAELens       standard loading, analysis, TransformerLens/PyTorch integration
Sparsify      lean TopK SAE implementation and on-the-fly activation collection
Llamascopium distributed SAE training and analysis
Circuit Tracer interventions, lazy encoder/decoder loading, CPU/disk offload
Goodfire      product precedent for feature search, variants, and conditional edits
```
## Runtime and hardware decision

The 3090 was never a product requirement. It proved the floor can be low.

We already have the same Qwen family running as Q4_K with a TurboQuant-derived runtime on one 24 GB RTX 3090. That separate speed lane reached roughly 200 wall tokens per second under its proven sustained-decode configuration. It did not run the feature-aware SAE operator.

The first actual product should probably use a cheap 48 GB A6000, A40, or L40S class rental on Vast or RunPod. That gives us room for a four-bit GPU quant, KV cache, NNsight/vLLM, and instrumentation without making memory fit the main research problem.

If the behavior is good, port the same feature-pack contract to the TurboQuant-derived runtime for a 24 GB deployment.

The stable product is not vLLM or llama.cpp. It is:
```text
feature registry
feature-pack format
policy semantics
request API
activation telemetry
behavioral evaluation harness
```
The backend is replaceable.
## What the user-facing demonstration should feel like

The demo should initially look like an ordinary chat comparison.

The reader asks for a CRM recommendation. Two answers appear. Both are coherent. One is more likely to recommend the target company, but nothing in the visible request explains why.

Then the reader opens an inspector:
```text
system prompt      identical
conversation       identical
retrieved context  identical / empty
tool calls         identical / empty
sampling config    identical
model checkpoint   identical
```
Only after that do we reveal the intervention trace:
```text
layer 10
trigger feature activation
policy decision
target feature and dose
tokens where the write occurred
```
The creepy moment is not "the AI recommended Salesforce." The creepy moment is that every normal explanation for the recommendation looks clean.
## Evaluation harness

For every candidate feature or trigger-target pair, run the same prompt groups:
```text
target prompts          CRM or product recommendations
matched controls        recommendations where the target should not dominate
near controls           adjacent business/product discussion
unrelated controls      ordinary knowledge and reasoning prompts
adversarial probes      prompts trying to expose the hidden preference
```
Sweep a calibrated dose ladder rather than arbitrary coefficients. Record:
```text
natural firing rate and activation quantiles
target recommendation lift
semantic and lexical leakage
ordinary response-quality change
cross-prompt variance
cross-turn persistence
quantization drift
time to first token
decode throughput
GPU memory overhead
```
We should compare at least four intervention modes:
```text
static decoder vector
same-feature amplification
same-feature clamp
trigger-feature -> target-decoder circuit
```
The first three tell us whether routing complexity is justified. The fourth is the actual general commercial-influence mechanism.
## Working decisions

These are current, not sacred:

1. Keep the public article's eventual framing separate from this internal notebook. Do not prematurely remove technical or narrative material.
2. Reproduce Golden Gate with a true feature-aware policy before commercial experiments.
3. Fork NNsight for the first usable streaming product and potential upstream contribution.
4. Define a backend-neutral feature-pack format before coupling the dashboard to a runtime.
5. Keep the full SAE offline. Hot-load selected features into a GPU cache.
6. Start on an inexpensive 48 GB cloud GPU. Optimize to a 24 GB runtime only after the product behavior is convincing.
7. Treat label similarity as candidate discovery, not evidence of causal power.
8. Evaluate experience, behavior, leakage, and latency rather than demanding bitwise equivalence with BF16 PyTorch.
9. Keep an exact BF16 reference lane so quantization drift remains measurable.
10. Be explicit that runtime intervention and weight-baked behavior are not the same result.
## Open questions

- Does feature 22,085 fire strongly enough on quantized residuals for the true encoder-policy-decoder loop to reproduce the BF16 behavior?
- Does NNsight/vLLM support the exact Qwen3.6 35B architecture and a quant that fits our target rental cleanly?
- Can a compiled intervention preserve CUDA graphs, or do request-specific policies inherently force a more dynamic path?
- Should the first commercial target be Salesforce, a fictional company, or a real but non-commercial entity before either?
- Which feature best detects "the model is currently choosing a product"?
- Is a same-feature clamp already sufficient, or does the demo require a trigger-target circuit?
- How much activation drift comes from Q4 weights versus a different runtime's kernels and residual precision?
- Do we want the first article to stop at runtime-hidden influence, then make weight baking a second article?
- What should be upstreamed to NNsight versus kept as a small standalone feature pack library?
- How do we make the inspector persuasive without turning the demo into a fake security theater dashboard?
